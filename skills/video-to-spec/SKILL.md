# 视频制作规格

读 [项目约定](references/project-contract.md)、[制作预设](references/profiles.md) 和 [质量规则](references/quality.md)。读取当前讨论与 SPEC；本阶段负责整理，不重新访谈已有答案。

## 执行

1. 汇总用户已确认的目标、选项与参考。缺少会改变故事、人物或卖点的事实时，列最小待决问题；其他部分先写草稿。
2. 按 `assets/spec-template.md` 填 SPEC。每个镜头写清用途、目标秒数、景别、起态、动作、终态、机位/运镜、声音/台词、参考和衔接。画面与声音分栏。
3. 多镜头共用人物/产品/场景时，声明稳定 ID、必须保留的特征、场景固定点/顺序/相机侧；精确台词与广告事实有来源。已有视觉参考优先于原始模糊提示词。
4. 校验秒数总和、话语可说完的时间、开头 Hook、结尾 CTA，以及交付比例/分辨率/字幕语言/音轨。文字估时只算估计；语音出来后复听并修时轴。
5. 为尚未验证的动态变化指定最低成本的预演；动作复杂度超工具已知能力时标风险，不写成能保证实现。字幕与口型缺口写替代路径及验收方法。
6. 展示脚本、分镜和未决点。CHECKPOINT：内容具体可审查后才请求批准；用户确认后记录批准人、用户证据与当前 SPEC 的 SHA-256 与所用素材的 asset_bindings 快照。已有明确批准就复用证据。
7. 交给 `video-to-tickets`。不得把推荐候选标为 approved；不得因整理完成自动执行画布或生成。

## 改动

用户只改一行台词时，指出声音、字幕、可见说话人口型、镜头长度可能受影响；不把无关视觉决定全部解锁。
修改后重算SPEC及受影响TICKETS哈希；按用户本次明确修改指令继承对应批准并保留旧产物。只有新增或越界内容才请求确认，不因哈希变化重问同一改词。

## 失败分支

| 触发 | 第一处理 | 仍失败 |
| --- | --- | --- |
| 只有“更震撼” | 转成可看见/听见的两种具体变化 | 回 Grill 解决一个决定 |
| 时长与台词冲突 | 用实测语音/已有音频核时 | 提供删词或延长两个方案，不擅自删卖点 |
| 参考不一致 | 按用户批准的 ID 标主参考与冲突点 | 不混合出新人物或新产品 |
| 必要能力未知 | 明确效果目标和需验证的能力 | 留 blocked，不把失败写成通过 |

## 禁止

不要把 SPEC 直接写成 LibTV 参数；不要写冗长软件用户故事或新建工程架构；不要用形容词代替镜头行为。
不要悄改已批准声明来迎合某次输出，不把客户实拍替换成外观相似的虚构场所。

## 已授权的局部修订

用户明确的局部改词按项目约定“批准继承”执行：更新受影响文件的哈希并追加revision_evidence，保留未改素材批准、原预算上限和全部消费/尝试记录。只有超出原授权范围才请求新增批准；不得仅因文件哈希变化重复询问同一修改。
